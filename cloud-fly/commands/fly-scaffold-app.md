# Fly Scaffold App

Scaffold a new Fly.io application for a workload described as: **$ARGUMENTS**

## What to do

1. **Confirm app requirements.** Ask up to three clarifying questions if not obvious from the description:
   - What is the primary programming language and framework?
   - Which regions should the app target? (e.g., `iad` for US East, `lhr` for Europe, `nrt` for Asia)
   - Does the app need a database (Fly Postgres), object storage (Tigris bucket), or a cache (Fly Redis)?

   Do not wait for every detail. Make sensible defaults and document them. The user can adjust `fly.toml` after scaffold.

2. **Confirm scope** with one focused question if state is involved:
   - For stateful workloads: is a single primary region acceptable, or does the app need multi-region writes with `fly-replay` routing?

3. **Generate the project skeleton** in the current working directory (or a subdirectory the user specifies). Every scaffold must include:
   - A `fly.toml` with production-grade defaults (see below).
   - A `Dockerfile` appropriate for the language (multi-stage build, non-root user, no secrets in layers).
   - A `.github/workflows/deploy.yml` using `superfly/flyctl-actions` with a pinned `flyctl` version and a deploy token (`FLY_API_TOKEN`).
   - A `scripts/bootstrap-secrets.sh` that documents which secrets to set and provides `fly secrets set` commands with placeholder values.
   - A `scripts/setup-postgres.sh` (if Postgres is requested) that creates a least-privilege app user.
   - A `.gitignore` appropriate for the language.
   - A `README.md` with bootstrap + deploy + rollback commands.

4. **Wire production-grade defaults.** Do not generate demo-grade code:
   - HTTPS only: `force_https = true` on port 80.
   - No secrets in `fly.toml` or Dockerfile. All sensitive values use `fly secrets`.
   - Health check defined with `grace_period`, `interval`, and `timeout`.
   - `auto_stop_machines = "stop"` for stateless services. Note where `min_machines_running = 1` is recommended.
   - Deploy strategy: `bluegreen` for production, `rolling` for staging.
   - Image tagged by git SHA in the deploy workflow, not `:latest`.

5. **Print next steps** — the exact commands the user must run to bootstrap the app from zero:
   - `fly auth login` (if not authenticated)
   - `fly apps create <app-name>` (if not yet created)
   - Secret bootstrap: `bash scripts/bootstrap-secrets.sh`
   - Postgres create: `fly postgres create --name <db-name> --region <region>` (if needed)
   - Tigris bucket create: `fly storage create --name <bucket-name> --app <app-name>` (if needed)
   - `fly deploy` to launch the first machine.
   - Reminder: first deploy should target a staging app before production.

## File templates

### `fly.toml`

```toml
# fly.toml — generated by /fly-scaffold-app
# Adjust region, machine size, and service config to match your workload.

app = "<app-name>"
primary_region = "<primary-region>"    # e.g., "iad", "lhr", "nrt"

[build]
  dockerfile = "Dockerfile"

[env]
  # Non-sensitive configuration only. All secrets go in fly secrets.
  PORT = "8080"
  LOG_LEVEL = "info"
  ENVIRONMENT = "production"

[deploy]
  strategy = "bluegreen"
  # Uncomment if your app runs database migrations on deploy:
  # release_command = "<your-migration-command>"

[[vm]]
  size = "shared-cpu-2x"
  memory = "512mb"

[http_service]
  internal_port = 8080
  force_https = true
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 1

  [http_service.concurrency]
    type = "requests"
    hard_limit = 200
    soft_limit = 150

  [[http_service.checks]]
    grace_period = "10s"
    interval = "15s"
    method = "GET"
    path = "/healthz"
    timeout = "5s"

# Uncomment if this app uses a Fly Volume:
# [mounts]
#   source = "<app-name>_data"
#   destination = "/data"

# Uncomment to expose a Prometheus-compatible metrics endpoint:
# [[metrics]]
#   port = 9091
#   path = "/metrics"
```

### `Dockerfile` (multi-stage, non-root, no secrets in layers)

```dockerfile
# Dockerfile — multi-stage build; adjust base images for your language.
# Example shown for a Go app. Replace with Python / Node / Ruby as needed.

# Build stage
FROM golang:1.23-alpine AS builder

WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server ./cmd/server

# Runtime stage — distroless / minimal base
FROM alpine:3.21

# Run as non-root
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

WORKDIR /app
COPY --from=builder /app/server .

EXPOSE 8080

CMD ["./server"]
```

### `.github/workflows/deploy.yml`

```yaml
# .github/workflows/deploy.yml

name: Deploy to Fly

on:
  push:
    branches:
      - main

jobs:
  deploy:
    name: Deploy production
    runs-on: ubuntu-latest
    concurrency:
      group: ${{ github.workflow }}-${{ github.ref }}
      cancel-in-progress: true

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup flyctl
        uses: superfly/flyctl-actions/setup-flyctl@master
        with:
          version: "0.3.35"    # Pin this. Update deliberately.

      - name: Deploy
        run: |
          fly deploy \
            --app <app-name> \
            --strategy bluegreen \
            --remote-only \
            --image-label "sha-${{ github.sha }}"
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}
```

**Setup steps:**

```bash
# 1. Create a deploy token with expiry (not an org token)
fly tokens create deploy -a <app-name> --expiry 720h -n "github-actions-main"

# 2. Store the token output as a GitHub Actions secret named FLY_API_TOKEN
# GitHub repo → Settings → Secrets and variables → Actions → New repository secret
```

### `scripts/bootstrap-secrets.sh`

```bash
#!/usr/bin/env bash
# scripts/bootstrap-secrets.sh
# Bootstrap required secrets for <app-name> on Fly.
# Run once per environment after first creating the app.
# Replace placeholder values with real credentials before running.

set -euo pipefail

APP_NAME="<app-name>"

echo "Bootstrapping secrets for $APP_NAME..."

# Database connection string (Fly Postgres)
# After creating the Postgres cluster with fly postgres create,
# retrieve the connection URL with: fly postgres attach <db-name> --app <app-name>
# That command injects DATABASE_URL automatically.
# If connecting to an external database, set it manually:
# fly secrets set DATABASE_URL="postgres://appuser:CHANGEME@mydb.internal:5432/appdb" -a "$APP_NAME"

# Session / JWT signing key (generate a strong random value)
FLY_SECRET_SIGNING_KEY="$(openssl rand -hex 32)"
fly secrets set SIGNING_KEY="$FLY_SECRET_SIGNING_KEY" -a "$APP_NAME"

# Add additional secrets below as needed:
# fly secrets set STRIPE_API_KEY="sk_live_CHANGEME" -a "$APP_NAME"
# fly secrets set SENDGRID_API_KEY="SG.CHANGEME" -a "$APP_NAME"

echo "Done. Run 'fly secrets list -a $APP_NAME' to verify."
echo "IMPORTANT: Store generated values in your team's password manager."
```

### `scripts/setup-postgres.sh` (if Postgres requested)

```bash
#!/usr/bin/env bash
# scripts/setup-postgres.sh
# Create a least-privilege Postgres application user.
# Run after fly postgres create and fly postgres attach.

set -euo pipefail

DB_APP="<db-app-name>"
APP_USER="appuser"
APP_DB="<app-db-name>"

echo "Creating application user '$APP_USER' in Fly Postgres..."

fly postgres connect -a "$DB_APP" <<-EOSQL
  -- Create application user (not superuser)
  CREATE USER "$APP_USER" WITH PASSWORD 'CHANGEME_ROTATE_IMMEDIATELY';

  -- Grant access to the app database only
  GRANT CONNECT ON DATABASE "$APP_DB" TO "$APP_USER";
  GRANT USAGE ON SCHEMA public TO "$APP_USER";
  GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO "$APP_USER";
  ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO "$APP_USER";
  GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO "$APP_USER";
  ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO "$APP_USER";
EOSQL

echo "User created. Rotate the password now and store it in fly secrets:"
echo "  fly secrets set DATABASE_URL=\"postgres://$APP_USER:NEWPASSWORD@<db-app-name>.internal:5432/$APP_DB?sslmode=require\" -a <app-name>"
```

## Multi-region machine config (if requested)

After the initial deploy to `primary_region`, scale to additional regions:

```bash
# Add machines in additional regions
fly scale count 1 --region lhr --app <app-name>
fly scale count 1 --region nrt --app <app-name>

# Verify placement
fly status --app <app-name>
```

For stateful apps with write routing, add `fly-replay` response headers in the application for write operations:
- On a replica region, the app detects it is not the primary and responds with `fly-replay: region=<primary-region>`.
- Fly Proxy replays the request to the primary region.

## After scaffolding

- Hand off to the `fly-architect` sub-agent for a review of the generated `fly.toml` and architecture before the first production deploy.
- Run `fly-security-reviewer` once the first environment is live to confirm no secrets are exposed and the network posture is correct.
- Remind the team: Fly Postgres is managed-by-you. Schedule a restore drill for the first Postgres backup after launch.
- For the first production deploy, use a staging app (`fly deploy -a <app-name>-staging`) to validate before touching production.
