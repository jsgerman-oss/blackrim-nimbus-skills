# Render Scaffold Blueprint

Scaffold a `render.yaml` Blueprint and GitHub Actions CI pipeline for a workload described as: **$ARGUMENTS**

## What to do

1. **Confirm the workload shape.** Ask up to three clarifying questions if the description is ambiguous:
   - What language / runtime? (Node, Python, Ruby, Go, Rust, Docker image)
   - What region? (`oregon` / `ohio` / `frankfurt` / `singapore`) — default is `oregon`.
   - Are there services that should be Private Services rather than Web Services? (Any service that is only called by other Render services should be a Private Service.)

2. **Generate the Blueprint.** Create `render.yaml` in the current directory with the full structure below. Every scaffold must include:
   - A Web Service for the main HTTP server.
   - A Private Service if there is an internal API.
   - A Background Worker for queue consumers.
   - A Cron Job for scheduled tasks.
   - Managed Postgres (Standard plan for PITR + HA).
   - Managed Redis (Starter plan default; upgrade to Standard if sessions or pub/sub are critical).
   - A `previews:` block for PR preview environments with `previewsExpireAfterDays: 7`.
   - `fromGroup:` references for all secrets (no inline `value:` for credentials).
   - `healthCheckPath:` on all Web and Private Services.
   - `autoscaling:` with explicit `minInstances` and `maxInstances` on Standard+ services.

3. **Generate GitHub Actions workflows.** Create `.github/workflows/ci.yml` and `.github/workflows/deploy.yml`:
   - `ci.yml`: lint, test, and (for Docker) build + scan image on every push and PR.
   - `deploy.yml`: on merge to `main`, run CI first, then trigger Render deploy via API. No auto-deploy from the Render GitHub integration for production — always gate on CI passing.

4. **Print next steps** — the manual steps the user must take after the scaffold:
   - Create the Environment Group `prod-secrets` in the Render dashboard and populate credentials.
   - Connect the repository in the Render dashboard and select the Blueprint.
   - Add the Render API key as a GitHub Actions secret (`RENDER_API_KEY`) and the service ID (`RENDER_SERVICE_ID`).
   - Configure branch protection on `main`: require status checks to pass before merging.
   - Run a first deploy and verify the health check endpoint returns 2xx.
   - Verify that a PR preview environment is created when a test PR is opened.

### `.github/workflows/ci.yml`

```yaml
name: CI

on:
  push:
    branches: ["main", "staging"]
  pull_request:
    branches: ["main", "staging"]

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up runtime
        # Adapt this step to your runtime:
        # Node: actions/setup-node@v4 with node-version from .nvmrc
        # Python: actions/setup-python@v5
        # Go: actions/setup-go@v5
        uses: actions/setup-node@v4
        with:
          node-version-file: .nvmrc
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Type check
        run: npm run typecheck       # Remove if not applicable

      - name: Test
        run: npm test

  # Uncomment for Docker-based builds
  # docker-build-and-scan:
  #   runs-on: ubuntu-latest
  #   steps:
  #     - uses: actions/checkout@v4
  #     - name: Build image
  #       run: docker build -t ${{ github.sha }} .
  #     - name: Scan image
  #       uses: aquasecurity/trivy-action@master
  #       with:
  #         image-ref: ${{ github.sha }}
  #         severity: HIGH,CRITICAL
  #         exit-code: 1

  preview-deploy-check:
    runs-on: ubuntu-latest
    needs: lint-and-test
    if: github.event_name == 'pull_request'
    steps:
      - name: PR preview is handled by Render Blueprint
        run: |
          echo "Render will automatically provision a preview environment for this PR."
          echo "Check the Render dashboard or the PR status check for the preview URL."
```

### `.github/workflows/deploy.yml`

```yaml
name: Deploy to Production

on:
  push:
    branches: ["main"]

jobs:
  # CI must pass before deploy
  ci:
    uses: ./.github/workflows/ci.yml

  deploy:
    runs-on: ubuntu-latest
    needs: ci
    environment: production       # Requires a GitHub Actions environment with approval gate
    steps:
      - name: Trigger Render deploy
        env:
          RENDER_API_KEY: ${{ secrets.RENDER_API_KEY }}
          RENDER_SERVICE_ID: ${{ secrets.RENDER_SERVICE_ID }}
        run: |
          curl --fail -X POST \
            "https://api.render.com/v1/services/${RENDER_SERVICE_ID}/deploys" \
            -H "Authorization: Bearer ${RENDER_API_KEY}" \
            -H "Content-Type: application/json" \
            -d '{"clearCache": false}'

      - name: Wait for deploy and check health
        env:
          RENDER_API_KEY: ${{ secrets.RENDER_API_KEY }}
          RENDER_SERVICE_ID: ${{ secrets.RENDER_SERVICE_ID }}
        run: |
          echo "Deploy triggered. Monitor status in the Render dashboard."
          echo "Service: https://dashboard.render.com/web/${RENDER_SERVICE_ID}"
```

## Security defaults applied

- All credentials delivered via `fromGroup: prod-secrets` — no `value:` entries for secrets.
- Internal APIs use `type: pserv` — not accessible from the public internet.
- Health check path required for zero-downtime deploys.
- `maxInstances: 5` prevents uncapped autoscale billing.
- `previewsExpireAfterDays: 7` prevents stale preview environments from accumulating.
- Production Postgres on Standard plan — enables PITR and HA.
- CI must pass before production deploy (`needs: ci` in deploy job).
- GitHub Actions `environment: production` adds a manual approval gate before deploy.

## After scaffolding

- Hand off to the `render-architect` sub-agent for a review of the generated Blueprint before the first deploy.
- Run `render-security-reviewer` once the first environment is live, before opening traffic to the public.
- Remind the team to verify preview environments work on the first PR after Blueprint connection.
- Verify the health check endpoint (`/health`) responds with 2xx and reflects actual service readiness (not just HTTP 200 immediately on process start).
