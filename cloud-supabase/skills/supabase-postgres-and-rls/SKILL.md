# Supabase Postgres and Row Level Security

## When to use

- Designing a new schema for a Supabase project.
- Writing or auditing RLS policies for any table.
- Choosing between `session` and `transaction` connection pooling modes.
- Setting up database migrations via the Supabase CLI.
- Planning read replicas, preview branches, or PITR for a production project.
- Reviewing the built-in `anon`, `authenticated`, and `service_role` role model.

## The Supabase role model

Supabase ships three built-in Postgres roles that every developer must understand:

| Role | Who uses it | RLS bypass |
| --- | --- | --- |
| `anon` | Unauthenticated API requests (no JWT) | No |
| `authenticated` | Requests with a valid Supabase JWT | No |
| `service_role` | Server-side clients using the service key | **Yes** — bypasses all RLS |

`auth.uid()` returns the user's UUID from the JWT; `auth.role()` returns `'authenticated'` or `'anon'`. These are the two helpers you use inside policy expressions.

The `postgres` superuser role is available for migrations and administrative tasks but should not be used in application code.

## Row Level Security — the security spine

RLS is the primary data-access control mechanism in Supabase. The PostgREST API layer runs as the `anon` or `authenticated` role, meaning every query is subject to RLS policies. Without a policy, no row is returned and no write is accepted — **unless you have also explicitly granted table-level permissions**.

### Enable RLS on every table, without exception

```sql
-- Enable RLS — do this at table creation, not after
ALTER TABLE public.posts ENABLE ROW LEVEL SECURITY;

-- Force RLS even for the table owner (postgres role)
ALTER TABLE public.posts FORCE ROW LEVEL SECURITY;
```

`FORCE ROW LEVEL SECURITY` prevents the table owner from accidentally bypassing policies during debugging sessions. Apply it in production.

### Policy anatomy

```sql
-- SELECT policy: users see only their own rows
CREATE POLICY "users_select_own"
  ON public.posts
  FOR SELECT
  TO authenticated
  USING (user_id = auth.uid());

-- INSERT policy: authenticated users can insert rows they own
CREATE POLICY "users_insert_own"
  ON public.posts
  FOR INSERT
  TO authenticated
  WITH CHECK (user_id = auth.uid());

-- UPDATE policy: same ownership check
CREATE POLICY "users_update_own"
  ON public.posts
  FOR UPDATE
  TO authenticated
  USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid());

-- DELETE policy
CREATE POLICY "users_delete_own"
  ON public.posts
  FOR DELETE
  TO authenticated
  USING (user_id = auth.uid());
```

Key rules:
- `USING` filters rows for SELECT, UPDATE, DELETE (which rows are visible / eligible).
- `WITH CHECK` validates rows for INSERT and UPDATE (which rows can be written).
- Policies are additive — a row is accessible if **any** applicable policy permits it.
- Missing policies on an RLS-enabled table mean **zero rows** are accessible to that role.

### Multi-tenant / team patterns

```sql
-- Users belong to organizations; members can read org data
CREATE POLICY "org_members_select"
  ON public.documents
  FOR SELECT
  TO authenticated
  USING (
    org_id IN (
      SELECT org_id FROM public.memberships WHERE user_id = auth.uid()
    )
  );
```

For performance, materialize frequently-checked membership via a security-definer function rather than a correlated subquery:

```sql
CREATE FUNCTION auth.user_orgs() RETURNS SETOF uuid
  LANGUAGE sql STABLE SECURITY DEFINER AS $$
    SELECT org_id FROM public.memberships WHERE user_id = auth.uid();
  $$;

CREATE POLICY "org_members_select"
  ON public.documents FOR SELECT TO authenticated
  USING (org_id = ANY(ARRAY(SELECT auth.user_orgs())));
```

## Schema design defaults

- Use `uuid` primary keys generated by `gen_random_uuid()` (Postgres 13+) or `uuid_generate_v4()`.
- Always include `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` and `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`. Use a trigger to maintain `updated_at`.
- Reference `auth.users(id)` with `ON DELETE CASCADE` where a user row deletion should cascade.
- Keep application data in the `public` schema. Never put application tables in the `auth` or `storage` schemas (Supabase-owned; migrations may break them).
- Use Postgres constraints — `NOT NULL`, `CHECK`, `UNIQUE`, foreign keys — as the first line of data integrity, before application-layer validation.
- Prefer `text` over `varchar(n)` for strings; use a `CHECK` constraint if you need a length limit.
- Use `JSONB` for semi-structured data; add `GIN` indexes for queried keys.

## Migrations

Supabase CLI manages migrations as ordered SQL files. Never modify production schema without a migration.

```bash
# Start local dev stack
supabase start

# Create a new migration
supabase migration new add_posts_table

# Validate locally
supabase db reset

# Diff against remote to catch drift
supabase db diff --linked --schema public

# Push to linked remote
supabase db push
```

Migration files live in `supabase/migrations/<timestamp>_<name>.sql`. Commit these to version control — they are the authoritative schema history.

**Never** edit an existing migration that has been applied to any environment. Add a new migration instead.

## Database branching (preview branches)

Supabase Pro+ projects support database branching for pull request previews: each branch gets an isolated Postgres instance with migrations applied. Wire it with GitHub Actions:

```yaml
- uses: supabase/setup-cli@v1
- run: supabase link --project-ref $SUPABASE_PROJECT_REF
- run: supabase db push --linked
```

The Supabase GitHub integration can create / tear down branches automatically on PR open / close.

## Connection pooling — Supavisor

Supavisor is Supabase's connection pooler. Every hosted project ships with it.

| Mode | Use for | Persistent connections |
| --- | --- | --- |
| `session` | Long-lived app servers (Rails, Django) | Yes — one client = one Postgres connection |
| `transaction` | Serverless / Edge Functions | No — connection returned to pool after each transaction |

Connect via the Supavisor endpoint (port 6543 for transaction mode, 5432 for session mode) shown in your project's database settings.

**Critical for Edge Functions and serverless:** always use transaction mode (`?pgbouncer=true` in the connection string). Session mode will exhaust the Postgres connection limit rapidly.

```typescript
// Edge Function — transaction mode (pgbouncer=true disables prepared statements)
const client = postgres(Deno.env.get("DATABASE_URL")!, { prepare: false });
```

## Read replicas

Supabase Pro+ supports read replicas in additional regions. Route read-heavy queries (analytics, reports) to the replica connection string, keeping primary connections for writes.

## Point-in-time recovery

PITR is available on Pro+ projects. Enable it in the dashboard under Database → Backups. Default retention is 7 days; extend to 30 days for regulated workloads. PITR uses WAL archiving — ensure it's enabled before you need it.

## Custom Postgres extensions

Common extensions available on hosted Supabase (enable via `CREATE EXTENSION IF NOT EXISTS`):

- `pgvector` — vector similarity search (HNSW / IVF indexes)
- `pg_cron` — job scheduling
- `pg_net` — HTTP requests from Postgres (useful for Edge Function triggers)
- `pg_stat_statements` — query performance analysis
- `uuid-ossp` — legacy UUID generation (prefer `gen_random_uuid()` on PG 13+)
- `pgjwt` — JWT handling inside Postgres

## Anti-patterns

| Anti-pattern | What goes wrong |
| --- | --- |
| Table without RLS enabled | All rows are accessible to any role with table-level GRANT. One missing policy = full read exposure. |
| Policy that always returns `true` | Equivalent to no policy — every row accessible to every user. Define USING conditions explicitly. |
| `service_role` in client code | Bypasses all RLS. Any row in any table is readable/writable by any user who can inspect the bundle. |
| Editing migrations retroactively | Applied migrations are history. Changing them causes checksums to diverge from what was actually applied. |
| Schema changes via Studio SQL editor without migration | Drift between local and remote; next `db diff` produces noise; teammates' local stacks diverge. |
| Correlated subquery per-row in USING clause without index | Full table scan on the referenced table for every row — turns fast queries into slow ones at scale. |
| Using `postgres` role in application connection string | No RLS, no audit trail of application activity. Use `anon` or `authenticated` through the API, or a limited role for server-side. |
| Skipping `FORCE ROW LEVEL SECURITY` | Table owner (postgres) bypasses policies silently during debugging; easy to ship with a permissive connection. |

## Security defaults

- RLS enabled and forced on every table in `public` schema.
- Explicit policy for every role × operation combination you intend to support; no implicit permissiveness.
- `service_role` key stored only in server-side secrets (Supabase Vault, GitHub Actions secret, or environment variable injected at runtime). Never in client bundles or committed source.
- `anon` role granted only the permissions explicitly required (often just `SELECT` on lookup tables).
- Foreign keys with `ON DELETE RESTRICT` or `CASCADE` as appropriate; no orphaned foreign-key references.
- `auth.users` never queried directly from client code — use the `auth.*` helper functions.

## Observability defaults

- `pg_stat_statements` extension enabled for slow-query analysis.
- Supabase Dashboard → Database → Query Performance for a UI view of slow queries.
- Supabase Database Advisors (Dashboard → Advisors) for automated RLS and index recommendations.
- Log slow queries at the application layer; aim for p99 < 100 ms on user-facing queries.
- Track connection counts — alert when approaching the Supavisor limit for your compute tier.

## Cost considerations

- Database compute is the primary cost driver on Supabase. Right-size your project's compute add-on to match peak connection count.
- Egress from the database counts against bandwidth. Reduce row payloads with column selection; avoid `SELECT *` on wide tables.
- PITR and read replicas add cost — enable for prod, not dev/stage.
- Supavisor transaction mode enables more concurrent requests per connection limit — critical for serverless architectures where per-request connections would be cost-prohibitive.

## IaC hints

- Terraform provider: `supabase/supabase` — manages projects, settings, and secrets but not schema migrations (use CLI for those).
- Migration files are the canonical IaC for schema; commit them alongside application code in the same repo.
- Use `supabase/setup-cli` GitHub Action in CI to lint and validate migrations.
- Run `supabase db diff --linked` as a CI check to catch uncommitted schema drift.

## Verification checklist

- [ ] Every table in `public` schema has `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`.
- [ ] Every table has explicit policies for each role and operation that should be permitted.
- [ ] No policy uses an unconditional `USING (true)` without deliberate justification.
- [ ] `service_role` key is not present in any client-side code or committed environment file.
- [ ] Migrations are in `supabase/migrations/` and committed to version control.
- [ ] `supabase db diff --linked` produces no unexpected drift.
- [ ] Connection string for serverless / Edge Functions uses transaction mode (port 6543).
- [ ] `pg_stat_statements` is enabled; slow queries have been profiled at least once.
- [ ] PITR is enabled on the production project.
- [ ] Read replica configured and routed to for read-heavy query paths.
